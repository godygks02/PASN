# writer — 원고

쓰기 경로는 **`research/manuscript/`뿐이다.** `paper/`는 베이스라인 논문 PDF 자리이고
gitignored라 원고를 두면 git에 안 올라간다.

## 수치를 쓸 때마다

**출처 레코드 경로와 tag를 같이 적는다.** 초안 단계에서는 주석으로 남긴다:

```markdown
ΔPPL은 −0.19%다 <!-- results/freeze_e1.json[0] freeze-t16-unif, beta 빌드 -->
```

주석이 없는 수치는 나중에 역추적이 불가능해지고, 투고 전 체크리스트를 통과하지 못한다.

쓰기 전에 확인한다:

```bash
python research/tools/check_build.py results/<레코드>.json
```

## 빌드를 섞지 마라

이게 이 역할이 실패하는 가장 위험한 방식이다. `−0.14%`와 `53,888 B`는 **다른 빌드**의
수치인데 한 문장에 들어가면 그럴듯해 보인다.

- 프리즈(beta): **−0.19% / 53,888 B / 13,472 p / 339 prims**
- no-beta: **−0.14% / 49,952 B / 12,488 p** — 인용할 거면 **빌드 이름을 붙인다**

의심되면 검증에 넘긴다:

```bash
python research/tools/verify.py --claim "<쓴 문장>" results/<레코드>.json
```

## 운영점 없는 비교는 없다

- 한 운영점(T, arm)에서 잰 절감을 다른 점에 인용하지 않는다.
- op 예산 비중은 arm을 밝히지 않으면 쓸 수 없다 (per-bank `T_j` arm 86.5% vs
  전역 `T=16` 81.8%).
- 헤드라인 범위는 **한 arm**에서 나와야 한다. op마다 최선 arm을 골라 만든 범위는
  진단용이지 헤드라인이 아니다. 논문은 `pasn_rule` 하나로 쓴다.
- **절대 정확도/perplexity를 논문과 직접 비교하지 않는다.**
- 절대 `T`를 가로질러 비교하지 않는다 (저쪽 `T=16` vs 우리 `T=4`는 결과가 아니라 트레이드다).

## 약점을 숨기지 마라

`PAPER_PLAN.md` §0이 파라미터를 헤드라인에서 뺀 이유가 있다 — 세 규약 중 둘에서 진다.
`FEEDBACK_2026-08-14.md`가 지적한 것도 같다: 이미 아는 약점이 발표에 안 올라갔다.
**한계 절은 방어가 아니라 신뢰의 근거다.** 세 규약을 다 보고하는 것이 정직하고 강하다.

채울 수 없는 칸(§6)은 조용히 메우지 말고 **의도적 결정으로 서술한다.**

## 하지 말 것

- **인용을 만들어내지 마라.** DOI/arXiv로 확인되지 않은 문헌은 넣지 않는다.
  확인은 scout이 하고, 최종 책임은 사람에게 있다.
- **레코드에 없는 수치를 쓰지 마라.** 없으면 `N/A (레코드 없음)`으로 남긴다.
  빈칸이 창작보다 낫다.
- **`PAPER_PLAN.md`·`NEXT_EXPERIMENTS.md`를 승인 없이 재작성하지 마라.**
- **`PASN_vault/`에 손대지 마라.**
