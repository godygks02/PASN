# experiment-report — 레코드에서 결과 문서로

`results/<실험>.md`를 쓴다. 입력은 `results/<실험>.json`과 `logs/`의 원본 로그뿐이다.

## 첫 번째 규칙

**로그와 레코드에 없는 수치는 쓰지 않는다.** 누락된 값은 `N/A (레코드에 없음)`으로
남긴다. 빈칸이 창작보다 낫다 — 그리고 빈칸 자체가 "이건 안 쟀다"는 정보다.

기억이나 대화 맥락에서 수치를 가져오지 마라. 런을 돌린 세션의 말이 아니라
**파일이 진실원이다.**

## 절차

### 1. 빌드부터 확인한다

```bash
python research/tools/check_build.py results/<실험>.json
```

문서 맨 위에 판정을 적는다. `??`나 `NAME`이면 그걸 제목 근처에 명시한다 —
나중에 이 문서에서 수치를 가져다 쓸 사람이 가장 먼저 봐야 할 것이다.

### 2. 운영점을 먼저 쓴다

수치보다 운영점이 먼저다. `n_steps`, `ctx`, `stride`, `eval_mode`, arm, backend.
이게 없으면 아래 표 전체가 인용 불가능해진다.

### 3. 정확도와 비용을 같이 낸다

한쪽만 쓰면 등정확도 비교를 할 수 없고, 등정확도가 아니면 비용 비교는 의미가 없다.
`delta_pct`와 `spikes_per_token`·`stored_bytes`를 같은 표에 둔다.

### 4. 모순을 찾는다

**헤드라인 필드만 보고 파일을 닫지 마라.** 같은 JSON 안에 헤드라인과 모순되는 값이
들어 있던 적이 있다 — `5.27×` 옆에 엄격 계상 2.871 mJ가 있었고, 그건 MBE 스파이크-온리
1.413 mJ보다 2.03× 나쁘다. `by_kind`, `ops_per_input`, `stored_by_role`을 다 본다.

net loss인 항목이 있으면 **표에 남긴다.** 10개 중 5개가 net loss였는데 발표에는
안 올라간 적이 있다.

### 5. 실패한 런도 쓴다

`status: "failed"` 레코드를 빼지 마라. 무엇이 안 됐는지가 탐색 공간을 정의한다.

## 형식

```markdown
# <실험 ID> — <한 줄 요약>

레코드: `results/<실험>.json` · 빌드: **beta (프리즈)** / no-beta / ⚠️ 변종
운영점: T=16, arm=unif, stride=1024, backend=mbe_pasn, model=gpt2-medium

## 결과

| tag | ΔPPL | spikes/token | bytes | params |
|---|---:|---:|---:|---:|
| freeze-t16-unif | −0.187% | 4,690,321 | 53,888 | 13,472 |

## 반증 조건 대조

카드의 반증 조건이 무엇이었고, 통과했는가. 놓쳤으면 **놓쳤다고 적는다.**

## 모순 / net loss

## 안 잰 것

N/A로 남은 칸과, 그게 왜 비었는지.
```

## 쓰지 말 것

- **`results/`의 기존 JSON 레코드를 수정하지 마라.** 새 문서는 `.md`로 따로.
- **`logs/`의 원본 로그를 수정하지 마라.** 재현성의 근거다.
- **해석을 결론으로 올리지 마라.** 주장이 되려면 `verify.py`를 통과해야 한다.

## 다음 단계

문서를 쓴 뒤, 헤드라인이 될 주장은 교차모델 검증에 넘긴다:

```bash
python research/tools/verify.py --claim "<주장>" results/<실험>.json
```
